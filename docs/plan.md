# Implementation Plan & Execution Record

## How the Work Was Split into Sessions

The work was divided into 6 focused phases:

1. **Session 1: Scaffolding, Core Infrastructure & Database Schema (Phases 1 & 2)**
   - Initialized Git repository and environment configuration (`requirements.txt`, `.env.example`).
   - Defined SQLAlchemy models for all 7 entities (`User`, `Unit`, `RentPayment`, `MaintenanceRequest`, `MaintenanceRequestContractor`, `MaintenanceTimelineEvent`, `DismissedRentAlert`).
   - Initialized and configured Alembic with dynamic connection URL and autogenerated the initial migration script.
   - Implemented Bcrypt password hashing and PyJWT authentication primitives.

2. **Session 2: Domain Services & Business Rules Engine (Phase 3)**
   - Built `auth_service` and `unit_service` (with soft-delete archive/restore).
   - Built `rent_service` with 5-day grace period overdue calculations, bulk rent matching classification (`matched`, `underpaid`, `overpaid`, `unmatched`), and CSV generation.
   - Built `maintenance_service` with the strict 4-state lifecycle engine, contractor assignment prerequisite check for `SCHEDULED`, and immutable timeline logging.
   - Built `dashboard_service` aggregating headline KPIs, breakdowns, and 8-week resolution trends.

3. **Session 3: FastAPI REST API & Authorization Layer (Phase 3 Continued)**
   - Created REST routers for `/auth`, `/units`, `/rent`, `/maintenance`, and `/dashboard`.
   - Wired server-side dependencies (`require_manager`, `require_contractor`) to enforce HTTP 403 / 401 boundaries.
   - Implemented server-side search, filtering, sorting, and pagination on maintenance requests.

4. **Session 4: Realistic Seed Data & Automated Test Suite (Phases 4 & 6)**
   - Developed `backend/app/seed.py` with multi-month demo data, active/vacant/archived units, and varied maintenance lifecycles.
   - Wrote 23 automated tests covering auth, unit CRUD, contractor 403 rejections, lifecycle rule validations, contractor isolation, bulk rent classification, and timeline immutability.
   - Executed test suite with 100% pass rate.

5. **Session 5: Streamlit Frontend Presentation Layer (Phase 5)**
   - Created `frontend/api_client.py` strictly communicating via HTTP REST calls.
   - Developed `frontend/styles.css` custom design system.
   - Built role-based views: Login with 1-click demo buttons, Manager Dashboard, Units Portfolio, Rent Roll & Bulk Processing, Maintenance Ticket Inspector with timeline, and Contractor Workspace.

6. **Session 6: Verification & Complete Documentation (Phases 7 & 8)**
   - Validated server and frontend endpoints live.
   - Completed all 5 required documentation files under `docs/` and updated `SUBMISSION.md`.

---

## Build Order and Rationale

We built **backend-first, dependencies-inward**:
1. **Database Schema & Models first**: Everything in property management revolves around relational integrity (units to payments, requests to contractors and timelines). Getting the data model right prevented refactoring later.
2. **Business Services second**: Enforcing business rules (e.g. grace period, lifecycle transitions) in pure Python services allowed immediate testability before attaching API endpoints.
3. **FastAPI Endpoints third**: Exposing clean REST contracts with Pydantic validation and HTTP status codes (400, 401, 403, 404, 409).
4. **Automated Tests fourth**: Testing all backend endpoints, role boundaries, and business rules before building the frontend ensured no regressions.
5. **Streamlit Frontend fifth**: Since the frontend is purely a consumer of the API, having verified REST endpoints made UI integration fast and reliable.

## What We Deliberately Cut When Budgeting Time

1. **Email Sending Service (SMTP/SendGrid)**:
   - Cut in favor of prominent in-app navigation count badges and dashboard alert banners for overdue rent and maintenance notifications.
2. **Multi-tenant Landlord Partitioning**:
   - Kept as an optional stretch goal. The core focus remained delivering a rock-solid, production-grade implementation of all 10 requirements.
3. **Custom Drag-and-Drop Kanban Board**:
   - Streamlit does not natively support drag-and-drop kanban boards without heavy React third-party components. We instead built a clean status transition selector with server-side validation error handling and immediate timeline updates.
